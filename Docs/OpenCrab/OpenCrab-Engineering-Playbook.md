## 2. 开发方法：三层模型

### 2.1 战略层（不改）

- 继续沿用 `OpenCrab-Roadmap.md` 与 `OpenCrab-Longterm-Roadmap.md`。
- 阶段顺序：Phase 0 → 1 → … → 7；每阶段以签收或核心交付完成作为进入下一阶段条件。
- 资源与优先级见 Roadmap 第 12 节。

### 2.2 执行层（每个需求只保留五项）

每个开发任务（不论由人还是 AI 发起）在开工前必须收敛为：

1. **目标**：一句话说明要达成什么结果。
2. **边界**：明确在哪个模块/接口/页面内改动，不扩散到哪些区域。
3. **DoD（Definition of Done）**：列出必须完成的条目（含接口、测试、文档若适用）。
4. **验证方法**：如何证明完成（如：跑通某 API、通过某 smoke、手工步骤）。
5. **回滚方式**：若上线或合并后出问题，如何回退（如：revert commit、关闭 feature、恢复配置）。

不再为小改动维护重型 Phase 文档包；大特性仍可引用对应 Phase Backlog/接口契约，但执行时以“五项”为单次任务卡内容。

### 2.3 实现层（默认工作流）

- **AI 先出草案**：接口签名、数据模型、或关键逻辑伪代码/实现草稿。
- **人工收敛**：确认接口/边界/策略，避免 AI 擅自扩大范围。
- **AI 生成实现与测试**：在已确认边界内补全代码与必要测试。
- **人工验收**：按 DoD 与验证方法执行，通过后再合并。

单次任务**不同时**跨架构、接口、UI 三大面；若必须跨，拆成多个小任务串行完成。

## 3. 小团队节奏

针对 1–3 人、以 AI Coding 为主的团队：

- **单主线 + 严格 WIP**：同时只保留 **1 个** in-progress 主任务。
- **任务粒度**：单任务尽量在 **0.5–2 天**内可完成，并具备可运行验证。
- **禁止悬空状态**：不接受“只改文档未改代码”或“只改代码不可验证”的中间态；每个任务结束点必须是“可运行且已按 DoD 验证”。
- **Phase 回顾频率**：每周至多一次对 Phase/路线图做轻量回顾；日常只维护轻量 todo 与验收结果。
- **交接**：若从 1 人扩展到 2–3 人，同一任务卡需注明负责人与验收人，且变更说明（见 `OpenCrab-Change-Checklist.md`）必须足以让队友复现与回滚。

---

## 4. DoD、验证与回滚

### 4.1 最小 DoD（每任务必达）

- 代码在指定模块/边界内完成，且符合仓库分层约定（见 `AGENTS.md` 或仓库规则）。
- 本地 `npm run build` 通过。
- 本地 `npm run test` 通过（若改动涉及后端/共享逻辑）。
- 若改动影响现有 smoke：对应 `npm run smoke:phase1` 或 `smoke:phase2` 通过。
- 若涉及接口或行为变更：已更新或确认接口契约/文档（见变更检查清单）。

### 4.2 验证方式优先级

1. **自动化优先**：能写进 `test` 或 `smoke` 的，必须通过自动化验证。
2. **无法自动化时**：在任务卡中写明手工验证步骤与预期结果，验收时按步骤执行并记录。
3. **仅文档变更**：无需跑 smoke，但若文档描述接口/阶段/能力边界，需与代码或配置一致。

### 4.3 回滚

- **代码**：单次提交尽量单一逻辑；回滚以 `git revert` 或还原分支为主。
- **配置/数据**：在 Runbook 或任务卡中注明回滚步骤（如：恢复某配置、禁用某 feature、数据迁移回滚方案）。
- **文档**：文档与代码同步变更时，回滚代码须同步回滚对应文档修改。

## 5. 与现有 Phase 文档的关系

- **Backlog / 接口契约 / 验收包 / RACI**：仍为 Phase 级权威来源；本手册不重写这些内容。
- **执行时**：从 Backlog 或需求中拆出的**单次开发任务**，按本文“执行层五项 + 实现层工作流 + 小团队节奏”执行，并用 `OpenCrab-Task-Template.md` 统一任务卡格式。
- **质量门槛**：提交前必须满足 `OpenCrab-Change-Checklist.md` 中的最小检查项；CI 已覆盖的 `build`/`test`/`smoke` 保持为主质量门。
