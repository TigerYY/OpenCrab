# OpenCrab 路线图

## 1. 目标

本路线图用于把 `OpenCrab` 从规划阶段推进到试点交付，再推进到可复制的企业产品。路线设计遵循一个原则：先证明单团队价值，再扩展治理与生态，而不是一开始做成大而全平台。

## 2. 阶段概览

| 阶段 | 时间建议 | 目标 | 主要产出 |
| --- | --- | --- | --- |
| Phase 0 | 2-4 周 | 明确试点与 V1 范围 | PRD、架构说明、试点方案 |
| Phase 1 | 4-8 周 | 建立最小技术闭环 | 工作区、模型接入、知识索引、审计、轻量 PR review、最小审批 |
| Phase 2 | 6-10 周 | 企业化增强 | 通用审批、增强技能治理、可观测性、异步任务 |
| Phase 3 | 8-12 周 | 规模化复制 | 模板化部署、私有技能仓、跨团队复用 |
| Phase 4 | 8-12 周 | 组织级治理 | SSO/IdP、组织级权限、数据分级、合规与密钥治理 |
| Phase 5 | 6-10 周 | 运营与质量平台 | 评测体系、效果基线、成本归因、组织级运营分析 |
| Phase 6 | 8-12 周 | 企业入口与生态 | IM/聊天入口、连接器扩展、流程入口统一 |
| Phase 7 | 12+ 周 | 平台化与商业基础 | 多租户、配额计费、HA/容灾、多集群、生态市场基础 |

## 3. Phase 0：产品验证

### 目标

- 选定试点团队。
- 收敛 V1 场景与不做项。
- 明确部署模式和安全边界。

### 必交付

- `OpenCrab PRD`
- `OpenCrab V1 范围清单`
- `OpenCrab 系统架构说明`
- `OpenCrab 部署与安全边界设计`

### 验收标准

- 试点团队和目标场景被确认。
- 内网模型接入方式和外发策略被确认。
- 企业版与 `OpenClaw` 的分层边界被确认。

## 4. Phase 1：最小可用版本

### 目标

构建一个部门级团队愿意试用的最小闭环。

### 范围

- 工作区创建与成员管理。
- IDE 入口和 Web 管理台。
- 内网模型接入和一个外部模型回退通道。
- Git 仓库和文档索引。
- 基础技能启停与工作区级版本锁定。
- 审计日志最小闭环。
- 轻量 PR review webhook/bot。
- 两类最小审批：高风险技能启用、受限内容外发。

### 核心里程碑

1. 完成工作区与会话映射。
2. 完成模型代理和基础路由。
3. 完成知识索引和问答链路。
4. 完成审计记录链路与审批挂起恢复机制。
5. 在试点团队中启用 IDE 入口、Web 管理台和轻量 PR review。

### Phase 1 验收标准

- 代码问答和文档问答可用。
- 新人 onboarding 问答可基于团队知识源返回带来源的答案。
- 至少一个真实仓库的 PR review 轻量闭环可用。
- 至少一个审计页面可以回溯请求。
- 管理员可控制技能可见性和模型出口。
- 高风险技能启用和受限外发请求可进入挂起审批并在审批后恢复。

## 5. Phase 2：企业化增强

### 目标

补齐企业采购真正关心的治理能力。

### 范围

- 通用审批流。
- 技能审批、灰度发布和多环境治理。
- 异步任务与后台作业。
- 质量与成本指标看板。
- 更完整的 PR review 集成。

### 核心里程碑

1. 技能治理模型上线。
2. 通用审批与高风险任务拦截上线。
3. 异步索引与 review 作业上线。
4. 使用指标与成本指标可视化。

### Phase 2 验收标准

- 第三方技能不再是“安装即用”，而是“治理后可用”。
- 高风险外发与高风险工具调用可审批。
- 管理员能看见成本和采纳趋势。

## 6. Phase 3：规模化复制

### 目标

让产品可以从一个试点团队复制到多个团队和多个场景。

### 范围

- 标准部署模板。
- 团队模板和默认策略包。
- 企业私有技能仓。
- 跨团队能力复用。

### 核心里程碑

1. 形成标准化部署文档。
2. 形成团队模板与默认策略。
3. 形成技能发布和审核流程。

### Phase 3 验收标准

- 新团队可以在标准模板上快速开通工作区。
- 技能与策略可复用而不需要重复配置。
- 产品具备从单团队走向多团队部署的基础。

### Phase 3 当前进展

- **部署模板（E1）**：docker-compose 编排与健康检查、部署文档与 compose-smoke 已就绪。
- **团队模板（E2）**：工作区模板 API 与管理台 Templates 入口、从模板创建工作区已就绪。
- **后续**：企业私有技能仓、跨团队能力复用。

## 7. Phase 4：组织级治理

### 目标

从工作区级治理升级到组织级统一策略与合规能力，满足企业 IdP、数据分级与密钥管理要求。

### 范围

- 组织身份接入（SSO/IdP、SCIM 或等价同步）。
- 组织级权限与策略（跨工作区的角色与策略继承）。
- 数据分级、保留策略与合规策略。
- 密钥/数据治理（KMS、BYOK 或等效能力）。

### 核心里程碑

1. 完成 IdP/SSO 接入与组织-工作区映射。
2. 组织级策略与审计策略上线。
3. 数据分级与保留策略可配置并生效。
4. 密钥与敏感数据治理方案落地。

### 进入条件

- Phase 3 签收或 E3/E4 核心交付完成。
- 至少一个试点对组织级治理有明确需求。

### Phase 4 验收标准

- 企业可通过 IdP 统一登录并映射到工作区/角色。
- 组织管理员可配置跨工作区的策略与合规策略。
- 数据分级与保留策略可审计、可追溯。

## 8. Phase 5：运营与质量平台

### 目标

把可观测从“能看”升级为“能做运营决策”，建立效果评测与成本归因能力。

### 范围

- 评测体系与效果基线（eval、基准集、A/B）。
- 效果治理（prompt/版本管理、安全红队或等效）。
- 成本归因与 showback/chargeback 基础。
- 组织级运营分析与告警闭环。

### 核心里程碑

1. 效果评测流水线与基准集上线。
2. 成本按工作区/模型/用途可归因。
3. 组织级运营看板与告警规则可配置。

### 进入条件

- Phase 4 签收或组织级治理核心能力就绪。
- 运营/技术管理方对效果与成本分析有明确需求。

### Phase 5 验收标准

- 管理员能基于评测与成本数据做容量与策略决策。
- 关键指标具备告警与升级路径。

## 9. Phase 6：企业入口与生态扩展

### 目标

扩大触达面，统一企业内入口与连接器，支撑更多场景。

### 范围

- 企业 IM/聊天入口（机器人、成员侧 Web 对话）。
- 连接器扩展（Jira、飞书/Slack、工单、知识库 SaaS 等）。
- 流程入口统一与编排基础。

### 核心里程碑

1. 至少一个企业 IM 或 Web 对话入口上线。
2. 2–3 类新连接器（非 Git/Docs/PR）可用。
3. 入口与工作区/权限策略打通。

### 进入条件

- Phase 5 签收或运营与质量平台核心就绪。
- 业务方对多入口、多数据源有明确需求。

### Phase 6 验收标准

- 用户可从企业 IM 或统一 Web 入口使用能力。
- 新连接器数据可参与检索/审批/审计链路。

## 10. Phase 7：平台化与商业基础

### 目标

支撑多租户运营、商业化与高可用，为规模化与生态打基础。

### 范围

- 多租户运营与配额管理。
- 计费/分摊与 showback/chargeback 深化。
- HA、备份恢复、容灾与多集群/多地域基础。
- 生态市场基础（技能/策略发布、审核、分发）。

### 核心里程碑

1. 多租户隔离与配额体系上线。
2. 计费或分摊数据可出账。
3. HA 与备份恢复方案落地。
4. 技能/策略市场或内部分发流程就绪。

### 进入条件

- Phase 6 签收或入口与生态核心就绪。
- 商业或平台团队对多租户/计费/可靠性有明确需求。

### Phase 7 验收标准

- 多团队/多租户可安全隔离使用。
- 关键服务具备 HA 与可恢复能力。
- 具备面向内部的技能/策略分发与治理流程。

## 11. 阶段依赖与优先级建议

- **依赖关系**：Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5 → Phase 6 → Phase 7；建议按序推进，每阶段签收或核心交付后再进入下一阶段。
- **近程优先**：Phase 3 收口（E3 私有技能仓、E4 跨团队复用）+ Phase 4 组织级治理。
- **中远程**：Phase 5（运营与质量）→ Phase 6（入口与生态）→ Phase 7（平台化与商业）。
- **可并行探索**：Phase 5 的评测与 Phase 4 的合规可在不同角色下并行调研，但正式投入建议仍按阶段顺序。

## 12. 资源投入建议

### 最小团队配置

- 产品/项目负责人 1 人。
- 全栈或平台工程师 1-2 人。
- AI/后端工程师 1-2 人。
- 前端工程师 1 人。
- 安全/平台支持 0.5-1 人。

### 优先级建议

优先把工程投入放在：

- 工作区与控制面。
- 模型代理与安全边界。
- 知识索引与检索质量。
- 审计与治理闭环。

不要优先放在：

- 花哨的多智能体编排。
- 复杂自动化工作流广泛扩张。
- 过重的行业定制。

## 13. 风险与阶段性应对

| 风险 | 最容易出现的阶段 | 应对 |
| --- | --- | --- |
| 范围膨胀 | Phase 0-1 | 严格限制核心场景数量 |
| 内网模型效果不足 | Phase 1 | 保留受控外部模型回退 |
| 上游变更影响适配 | Phase 1-2 | 保持适配层稳定边界 |
| 安全质疑导致试点停滞 | Phase 1-2 | 优先交付审计与审批能力 |
| 扩展时运维复杂度陡增 | Phase 3 | 模板化与标准化部署 |

## 14. 决策建议

如果资源有限，最推荐的执行顺序是：

1. 先完成 `Phase 0` 文档与试点确认。
2. 再完成 `Phase 1` 的最小问答与审计闭环。
3. 只有当试点团队形成正反馈后，再进入审批、技能仓和多团队复制。

## 15. Phase 2 签收与进入 Phase 3 准入条件

Phase 2 开发已完成，进入签收/运营窗口。进入 Phase 3 前需满足：

1. **签收闭环**：Phase 2 关闭评审（`OpenCrab-Phase2-Closeout-Review.md`）已获产品/技术签收。
2. **回归可用**：执行 `npm run smoke:phase2`（需先启动 control-plane）可重复通过。
3. **交付物齐备**：Phase 3 启动包（Backlog、接口契约、验收标准、RACI/DRI）已产出或已排期。

详见 `OpenCrab-Phase2-Closeout-Review.md` 第 4 节。Phase 3 已按上述条件启动，E1/E2 MVP 已交付。

## 16. 结论

`OpenCrab` 的路线图应坚持“小范围试点、强治理优先、渐进扩展”的策略。产品价值会先体现在单团队的知识问答、代码评审和新人 onboarding 上，然后再逐步扩展到技能生态和更复杂的企业工作流。
