# OpenCrab 路线图

## 1. 目标

本路线图用于把 `OpenCrab` 从规划阶段推进到试点交付，再推进到可复制的企业产品。路线设计遵循一个原则：先证明单团队价值，再扩展治理与生态，而不是一开始做成大而全平台。

## 2. 阶段概览

| 阶段 | 时间建议 | 目标 | 主要产出 |
| --- | --- | --- | --- |
| Phase 0 | 2-4 周 | 明确试点与 V1 范围 | PRD、架构说明、试点方案 |
| Phase 1 | 4-8 周 | 建立最小技术闭环 | 工作区、模型接入、知识索引、审计、轻量 PR review、最小审批 |
| Phase 2 | 6-10 周 | 企业化增强 | 通用审批、增强技能治理、可观测性、异步任务 |
| Phase 3 | 8-12 周 | 规模化复制 | 模板化部署、私有技能仓、跨团队复用 |
| Phase 4 | 6-10 周 | 团队复制与轻治理 | SSO-lite、工作区/策略/技能模板、轻治理与审计留痕 |
| Phase 5 | 6-10 周 | 质量闭环与采纳增长 | 最小评测基线、工作区级成本/采纳可见性、反馈闭环 |
| Phase 6 | 6-10 周 | 跨团队协作网络 | 共享目录、协作审批、单点入口或连接器深化 |
| Phase 7 | 12+ 周 | 企业扩展包 | 组织级治理深化、多租户/计费、HA/容灾、生态市场 |

## 3. Phase 0：产品验证

### 目标

- 选定试点团队。
- 收敛 V1 场景与不做项。
- 明确部署模式和安全边界。

### 必交付

- `OpenCrab PRD`
- `OpenCrab V1 范围清单`
- `OpenCrab 系统架构说明`
- `OpenCrab 部署与安全边界设计`

### 验收标准

- 试点团队和目标场景被确认。
- 内网模型接入方式和外发策略被确认。
- 企业版与 `OpenClaw` 的分层边界被确认。

## 4. Phase 1：最小可用版本

### 目标

构建一个部门级团队愿意试用的最小闭环。

### 范围

- 工作区创建与成员管理。
- IDE 入口和 Web 管理台。
- 内网模型接入和一个外部模型回退通道。
- Git 仓库和文档索引。
- 基础技能启停与工作区级版本锁定。
- 审计日志最小闭环。
- 轻量 PR review webhook/bot。
- 两类最小审批：高风险技能启用、受限内容外发。

### 核心里程碑

1. 完成工作区与会话映射。
2. 完成模型代理和基础路由。
3. 完成知识索引和问答链路。
4. 完成审计记录链路与审批挂起恢复机制。
5. 在试点团队中启用 IDE 入口、Web 管理台和轻量 PR review。

### Phase 1 验收标准

- 代码问答和文档问答可用。
- 新人 onboarding 问答可基于团队知识源返回带来源的答案。
- 至少一个真实仓库的 PR review 轻量闭环可用。
- 至少一个审计页面可以回溯请求。
- 管理员可控制技能可见性和模型出口。
- 高风险技能启用和受限外发请求可进入挂起审批并在审批后恢复。

## 5. Phase 2：企业化增强

### 目标

补齐企业采购真正关心的治理能力。

### 范围

- 通用审批流。
- 技能审批、灰度发布和多环境治理。
- 异步任务与后台作业。
- 质量与成本指标看板。
- 更完整的 PR review 集成。

### 核心里程碑

1. 技能治理模型上线。
2. 通用审批与高风险任务拦截上线。
3. 异步索引与 review 作业上线。
4. 使用指标与成本指标可视化。

### Phase 2 验收标准

- 第三方技能不再是“安装即用”，而是“治理后可用”。
- 高风险外发与高风险工具调用可审批。
- 管理员能看见成本和采纳趋势。

## 6. Phase 3：规模化复制

### 目标

让产品可以从一个试点团队复制到多个团队和多个场景。

### 范围

- 标准部署模板。
- 团队模板和默认策略包。
- 企业私有技能仓。
- 跨团队能力复用。

### 核心里程碑

1. 形成标准化部署文档。
2. 形成团队模板与默认策略。
3. 形成技能发布和审核流程。

### Phase 3 验收标准

- 新团队可以在标准模板上快速开通工作区。
- 技能与策略可复用而不需要重复配置。
- 产品具备从单团队走向多团队部署的基础。

### Phase 3 当前进展

- **部署模板（E1）**：docker-compose 编排与健康检查、部署文档与 compose-smoke 已就绪。
- **团队模板（E2）**：工作区模板 API、从模板创建工作区（自动复制审批策略与 PR Review 配置）、模板详情策略摘要、管理台 Templates 页已就绪。
- **策略包与运营（E4）**：审批策略导出/导入 API 与管理台入口、Phase 3 运营手册已交付；phase3-smoke 已接入 CI。
- **企业私有技能仓（E3）**：技能仓 API（GET registry/packages、GET registry/packages/:packageId/versions）、POST skills/packages 支持 sourceType=registry+sourceRef、管理台「技能仓」视图与「引入到工作区」闭环已交付；phase3-smoke 与 E2E 已覆盖。
- **可签收**：E3 已交付，Phase 3 彻底完成，可签收；签收后可进入 Phase 4。

## 7. Phase 4：团队复制与轻治理

### 目标

把当前单团队可用升级为「多个部门/工作组可复制部署」，保持扁平化组织模型，不做重型组织级平台。

### 范围

- **SSO-lite**：最小企业登录接入（OIDC 或 SAML 任选其一），不做复杂 SCIM 同步。
- 工作区模板、策略包、技能包、知识接入模板的完善与复用。
- 基础跨团队复用：模板复制、技能仓复用、策略导入导出（在 Phase 3 基础上增强）。
- 轻治理：统一审计留痕、基础保留策略、基础角色模型。

### 核心里程碑

1. 企业可通过 IdP 统一登录并映射到工作区/角色（SSO-lite 就绪）。
2. 新团队可通过模板快速开通工作区并复用策略与技能。
3. 审计与基础保留策略可配置、可追溯。

### 进入条件

- Phase 3 签收或 E3/E4 核心交付完成。
- 至少一个试点对「多团队复制」或「企业账号登录」有明确需求。

### Phase 4 验收标准

- 企业账号可统一登录并进入对应工作区。
- 新团队可在标准模板上快速开通并复用策略与技能。
- 审计留痕与基础保留策略可审计、可追溯。

## 8. Phase 5：质量闭环与采纳增长

### 目标

让试点团队能判断「有没有效果、值不值得继续扩」，不做重型运营平台，先做工作区级可见性与反馈闭环。

### 范围

- 面向 2–3 个核心场景的最小评测基线。
- 工作区级使用、命中率、满意度、成本可见性。
- Prompt/模板/技能版本的轻量回溯能力。
- 反馈闭环：失败样本回流、人工标注入口、低成本复盘报表。

### 核心里程碑

1. 核心场景最小评测基线可用。
2. 工作区级采纳与成本可见。
3. 支持轻量版本回溯与反馈录入。

### 进入条件

- Phase 4 签收或团队复制与轻治理核心就绪。
- 试点或技术管理方对效果与成本可见性有明确需求。

### Phase 5 验收标准

- 管理员能基于工作区级数据判断效果与成本趋势。
- 支持失败样本与反馈的轻量回流与复盘。

## 9. Phase 6：跨团队协作网络

### 目标

围绕「偏扁平化组织」建设协作能力，不堆多入口，优先单点突破与共享复用。

### 范围

- 跨团队共享的知识包/技能包/模板目录。
- 协作审批与交接：部门内、部门间任务/策略共享。
- 仅选择一个真实高频入口或连接器做深化（如飞书/Slack 或 Jira 其一，由需求拉动）。
- 统一的协作对象模型：团队、项目、知识包、技能包。

### 核心里程碑

1. 跨团队共享目录与协作审批可用。
2. 至少一个企业入口或新连接器与工作区/权限打通。
3. 协作对象与工作区策略一致可审计。

### 进入条件

- Phase 5 签收或质量闭环核心就绪。
- 业务方对跨团队协作或某一入口/连接器有明确需求。

### Phase 6 验收标准

- 团队可共享与复用知识包/技能包/模板。
- 用户可从所选入口或连接器使用能力并受工作区策略约束。

## 10. Phase 7：企业扩展包

### 目标

在多个部门已稳定复用后，再进入重型企业扩展：组织级治理深化、多租户、计费、高可用与生态市场基础。

### 范围

- 组织级治理深化：SCIM、组织级策略继承、数据分级体系、合规深化、KMS/BYOK。
- 组织级运营中心、正式成本分摊/计费（showback/chargeback）。
- 多租户、HA、备份恢复、多集群/多地域。
- 更完整的内部市场/生态分发机制。

### 核心里程碑

1. 组织级身份与策略体系就绪。
2. 多租户隔离与配额/计费基础就绪。
3. 关键服务具备 HA 与可恢复能力。
4. 技能/策略内部分发与治理流程完善。

### 进入条件

- Phase 6 签收或跨团队协作核心就绪。
- 商业或平台团队对多租户、计费、可靠性或组织级合规有明确需求。

### Phase 7 验收标准

- 多团队/多租户可安全隔离使用。
- 组织级策略与数据治理可配置、可审计。
- 关键服务具备 HA 与可恢复能力；具备面向内部的技能/策略分发与治理流程。

## 11. 阶段依赖与优先级建议

- **依赖关系**：Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5 → Phase 6 → Phase 7；建议按序推进，每阶段签收或核心交付后再进入下一阶段。
- **近程优先**：Phase 3 收口（E3 私有技能仓、E4 跨团队复用）+ Phase 4 团队复制与轻治理（SSO-lite、模板与轻治理）。
- **中远程**：Phase 5（质量闭环与采纳增长）→ Phase 6（跨团队协作网络）→ Phase 7（企业扩展包）。
- **原则**：先让部门级/工作组级客户尽快体验可治理、可审计、可扩展的最小闭环；更高阶企业级功能在 Phase 7 按需扩展。能力分类依据见 [OpenCrab-Phase4plus-Capability-Classification](OpenCrab-Phase4plus-Capability-Classification.md)。

## 12. 资源投入建议

### 最小团队配置

- 产品/项目负责人 1 人。
- 全栈或平台工程师 1-2 人。
- AI/后端工程师 1-2 人。
- 前端工程师 1 人。
- 安全/平台支持 0.5-1 人。

### 优先级建议

优先把工程投入放在：

- 工作区与控制面。
- 模型代理与安全边界。
- 知识索引与检索质量。
- 审计与治理闭环。

不要优先放在：

- 花哨的多智能体编排。
- 复杂自动化工作流广泛扩张。
- 过重的行业定制。

## 13. 风险与阶段性应对

| 风险 | 最容易出现的阶段 | 应对 |
| --- | --- | --- |
| 范围膨胀 | Phase 0-1 | 严格限制核心场景数量 |
| 内网模型效果不足 | Phase 1 | 保留受控外部模型回退 |
| 上游变更影响适配 | Phase 1-2 | 保持适配层稳定边界 |
| 安全质疑导致试点停滞 | Phase 1-2 | 优先交付审计与审批能力 |
| 扩展时运维复杂度陡增 | Phase 3 | 模板化与标准化部署 |

## 14. 决策建议

如果资源有限，最推荐的执行顺序是：

1. 先完成 `Phase 0` 文档与试点确认。
2. 再完成 `Phase 1` 的最小问答与审计闭环。
3. 只有当试点团队形成正反馈后，再进入审批、技能仓和多团队复制。

## 15. Phase 2 签收与进入 Phase 3 准入条件

Phase 2 开发已完成，进入签收/运营窗口。进入 Phase 3 前需满足：

1. **签收闭环**：Phase 2 关闭评审（`OpenCrab-Phase2-Closeout-Review.md`）已获产品/技术签收。
2. **回归可用**：执行 `npm run smoke:phase2`（需先启动 control-plane）可重复通过。
3. **交付物齐备**：Phase 3 启动包（Backlog、接口契约、验收标准、RACI/DRI）已产出或已排期。

详见 `OpenCrab-Phase2-Closeout-Review.md` 第 4 节。Phase 3 已按上述条件启动，E1/E2 MVP 已交付。

## 16. 结论

`OpenCrab` 的路线图应坚持“小范围试点、强治理优先、渐进扩展”的策略。产品价值会先体现在单团队的知识问答、代码评审和新人 onboarding 上，然后再逐步扩展到技能生态和更复杂的企业工作流。
